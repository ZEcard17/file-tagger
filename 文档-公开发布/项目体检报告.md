## 2. 标签数据是怎么流的（一张图看懂）

```
                    ①  手动打标签
                    ②  自动标签规则（按名字/扩展名/路径）
                    ③  文件名规则（文件名里含标签名就自动打）
                              │
                              ▼
                    ┌───────────────────┐
                    │   file_tags 表     │   每个「文件×标签」一行
                    │   is_auto 标明来源 │   0手动 / 1继承 / 2规则 / 3文件名
                    └─────────┬─────────┘
                              │  ④ resync：顺着父标签往上补
                              ▼
                    ┌───────────────────┐
                    │  tag_relations     │   标签之间的父子关系（可以多父）
                    └─────────┬─────────┘
                              │  ⑤ 分类库成员 = 「关联标签 + 它的所有子孙」命中的文件
                              ▼
                    ┌───────────────────┐
                    │  分类库（图本/软件…）│  界面只读 cached_cnt 缓存计数
                    └───────────────────┘
```

四句人话：
- 打标签有 **3 条入口**，但最后都落到同一张 `file_tags` 表里，**并且都会自动补祖先**。
- 光写标签不补祖先 → 分类库、标签统计就会「看着少」。（这是老版本最大的坑）
- 分类库不是单独存文件列表，而是**按标签算出来的**（关联标签 + 子孙标签）。
- 界面上显示的分类数量是**缓存值**，由后台悄悄重算，所以偶尔会慢一拍。

## 3. 铁律（以后动任何东西前，先默念这几条）

1. **`is_auto` 有四种值**：0=手动、1=父标签继承来的、2=自动规则打的、3=文件名规则打的。
   写错值 → 重算时会被当成「不需要」删掉。
2. **`tags` 表里那列 `parent_id` 是废的**（实测全库 0 条有值）。
   真正的父子关系只在 `tag_relations`。别再往 `parent_id` 写。
3. **给文件加标签后必须做一次「补祖先」**（程序里的 `resync`）。
   直接用 SQL 插 `file_tags` 会漏祖先 → 分类库少文件。
4. **往父子关系里挂新标签前，先查它的祖先链里有没有别的分类库根标签。**
   血的教训：「阅读」同时挂在「软件」和「图本」下，我给「公版图书」挂到「阅读」下，
   结果 1507 本书顺着链条跑进「软件」库（995 → 2499）。
5. **`files.path` 全库唯一，而且是「区分大小写」的比较。**
   改路径要先查撞车；网盘路径在库里是**全小写**、本地路径保留原样。
6. **改完路径/标签，分类库计数不会自己变**，要等后台重算。
7. **文件夹类规则要用「路径」匹配（target=path），而且片段要够长。**
   写 `九宫格` 会把整个「纸质游戏」19500 个文件都吃掉；要写 `纸质游戏\九宫格99999张`。
8. **没有作用范围（scope）的规则是全局的，会污染所有库。**
9. **规则不是自动生效的**：改完规则要「重读标签」或「同步所有文件的标签链」。
